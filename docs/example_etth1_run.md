# Example Run: ETTh1 Multi-Column Agent Analysis

This page records a real run of the current `core-clean` branch on the generated 1000-row ETTh1 agent test set.

## Command

```powershell
python main.py --data data/ETTh1_agent_test.csv
```

No `--column` argument was supplied, so the agent inspected the dataset and analyzed all suitable numeric measurement columns.

## Dataset selected by the agent

- 1000 hourly rows
- timestamp column: `date` (excluded as a prediction target)
- numeric targets: `HUFL`, `HULL`, `MUFL`, `MULL`, `LUFL`, `LULL`, `OT`

The test set contains controlled missing values and artificial spikes generated by `scripts/prepare_etth1.py`. The raw CSV is preserved; preprocessing tools write chained working files under `outputs/processed/`.

## Decisions observed in this run

### Missing-value handling

The agent found missing values in `HUFL`, `MUFL`, `OT`, and `LULL`. It chose **linear interpolation** for all four columns, using the local time-series context rather than a global mean/median.

The updates were applied sequentially to one working CSV so earlier preprocessing decisions were preserved.

### Anomaly detection

The agent selected the **IQR rule with multiplier 1.5** for all seven target columns.

Detected counts in this run:

| Column | IQR flags |
|---|---:|
| HUFL | 36 |
| HULL | 1 |
| MUFL | 46 |
| MULL | 1 |
| LUFL | 11 |
| LULL | 3 |
| OT | 33 |

The agent decided to **keep the flagged points** instead of automatically replacing them. Its reasoning was that many flags appeared to be sustained operating regimes or normal low/high ranges rather than isolated sensor errors. It identified the artificial `OT` spike around index 180 as particularly suspicious but still chose not to alter it because it was far from the forecast boundary.

This illustrates an important design point: anomaly detection and anomaly handling are separate decisions.

## Forecast validation

The Python evaluation tool compared lightweight forecasting candidates with rolling one-step validation over 50 recent points. The LLM then selected the final method using the returned MAE/RMSE evidence.

| Column | Selected method | Validation MAE | 5-step forecast |
|---|---|---:|---|
| HUFL | EWM, alpha=0.7 | 1.075 | 13.6322 repeated |
| HULL | EWM, alpha=0.7 | 0.622 | 5.5667 repeated |
| MUFL | Last value | 0.710 | 9.061 repeated |
| MULL | EWM, alpha=0.7 | 0.493 | 3.1888 repeated |
| LUFL | Last value | 0.390 | 4.508 repeated |
| LULL | EWM, alpha=0.7 | 0.092 | 1.4255 repeated |
| OT | Last value | 0.635 | 34.4 repeated |

`linear_trend` performed poorly on the recent validation window and was rejected by the agent based on the measured errors.

## What this example demonstrates

The analysis strategy is not supplied through command-line flags. During the run the LLM observes tool outputs and makes several constrained decisions:

1. which numeric columns should be analyzed;
2. whether missing values require treatment and which imputation strategy to use;
3. which anomaly-detection tool/parameters to use;
4. whether detected anomalies should be kept or modified;
5. which forecasting candidate to select after numerical validation.

The Python tools perform the actual numerical operations, while the LLM acts as the decision layer that selects actions from the registered tool set.

## Current limitations revealed by the run

- The forecasting candidates are intentionally lightweight. `last` and EWM produce flat multi-step horizons and therefore do not model the clear daily periodic structure in ETTh1.
- A 50-point validation window provides useful local evidence but is not enough to establish general model superiority.
- IQR flags can mix actual sensor errors with legitimate operating-regime changes; a future version should use richer temporal/contextual evidence before deciding whether to modify an anomaly.
- The current prototype is intended to study the agent decision loop rather than claim state-of-the-art forecasting performance.
